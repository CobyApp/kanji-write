# Japanese & Chinese Word Glosses (4-language word parity) — Design + Plan

Date: 2026-06-27
Status: Approved (delegated) — combined design + plan (fast path)
Builds on: Korean word glosses slice. Completes word meanings to en/ko/ja/zh,
matching the kanji-level 4-language glosses.

## 1. Purpose

Words currently have en + ko meanings. Add ja and zh so the study card shows
word meanings in any of the four app languages. Generated by LLM (one batch
agent emits both ja and zh per word), loaded into `word_gloss(lang='ja'|'zh')`.

This doc is the CONSUMING side (pipeline + app). The generation run producing
`sources/word_glosses_jazh.jsonl` is a separate (already-launched) controller step.

## 2. Components (pipeline)

- Generated artifact: `data-pipeline/sources/word_glosses_jazh.jsonl` — one JSON
  per line `{"id": <word_id>, "ja": "<日本語の意味>", "zh": "<中文释义>"}`.
  Committed via `.gitignore` negation (like the ko file).
- `kanjipipe/ingest/word_glosses.py`: add `parse_word_jazh(path) -> list[tuple[int, str|None, str|None]]`
  — tolerant JSONL; require integer `id` (reject bool); `ja`/`zh` stripped, empty→None;
  skip lines with no id. (Keep the existing `parse_word_glosses` for ko.)
- `kanjipipe/loader.py`: `load_word_jazh_glosses(conn, entries)` — for each
  `(word_id, ja, zh)`, insert a `word_gloss(word_id, 'ja', ja)` row if `ja`, and a
  `(word_id, 'zh', zh)` row if `zh`.
- `kanjipipe/build_db.py`: add optional trailing kwarg `word_jazh_path=None`; load
  after `load_word_ko_glosses`. `main()` adds `--word-jazh` default
  `sources/word_glosses_jazh.jsonl`.
- Fixture + tests.

## 3. Components (app)

- `SharedModels.WordEntry` gains `meaningJa: String?`, `meaningZh: String?`.
- `DictionaryClient.words` live: per word also fetch `lang='ja'` and `lang='zh'`
  word glosses → `meaningJa`/`meaningZh`.
- `KanjiDetail.wordMeaning(_ word, _ language)` extends to all four:
  `.ko → meaningKo ?? meaningEn`; `.ja → meaningJa ?? meaningEn`;
  `.zh → meaningZh ?? meaningEn`; `.en → meaningEn`. (View already calls it.)

## 4. Testing

- `parse_word_jazh`: valid lines → `(id, ja, zh)`; missing ja or zh → None for
  that field; blank/malformed/missing-id skipped; whitespace → None.
- `load_word_jazh_glosses`: seed a word, load `(id, "やま", "山")` → `ja`/`zh`
  word_gloss rows exist; a `(id, None, "山")` inserts only zh.
- `build_db` integration: pass a small `word_glosses_jazh.jsonl` fixture; assert a
  known word has ja and zh glosses.
- App: `wordMeaning` unit test extended (ja→ja, zh→zh, fallback to en when absent);
  `DictionaryClient` integration asserts `words` returns `meaningJa`/`meaningZh`
  (lands after the regen/re-bundle — until then assert nil; flip after bundle).
- Pipeline + app suites green.

## 5. Build order

1. Pipeline: `parse_word_jazh` + `load_word_jazh_glosses` + `build_db`
   `word_jazh_path` + fixtures/tests + `.gitignore` negation (TDD).
2. App: `WordEntry.meaningJa/meaningZh` + `DictionaryClient.words` fetch +
   `wordMeaning` 4-way + tests (TDD).
3. (Controller, parallel) Generation: 102 batches over `/tmp/word_in/*` →
   `{id, ja, zh}` → `/tmp/word_jazh_out/*` → assemble
   `sources/word_glosses_jazh.jsonl`; rebuild `out/kanji.sqlite` with
   `--word-jazh`; re-bundle; flip the app integration assertions; verify samples.

## 6. Non-Goals / Follow-on

zh-Hant; per-sense word glosses; word frequency. After this, word meanings are
en/ko/ja/zh — full parity with kanji glosses.
