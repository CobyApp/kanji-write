# Korean Word Glosses — Design + Plan

Date: 2026-06-27
Status: Approved (delegated) — combined design + plan (fast path)
Builds on: vocabulary slice (JMdict `word`/`word_gloss`) + LLM-gloss pattern.

## 1. Purpose

Add Korean (ko) meanings for the ~25k JMdict words so the study card shows word
meanings in Korean (alongside the existing English). Generated by LLM (batched
subagents), keyed by `word.id`, loaded into `word_gloss(lang='ko')`.

This doc covers the CONSUMING side (pipeline ingester + loader + app display).
The generation run (producing `sources/word_glosses_ko.jsonl`) is a separate
controller step after this is merged.

## 2. Components (pipeline)

- Generated artifact: `data-pipeline/sources/word_glosses_ko.jsonl` — one JSON
  per line `{"id": <word_id>, "ko": "<Korean meaning>"}`. Committed (curated,
  non-deterministic) via a `.gitignore` negation, like `llm_glosses.jsonl`.
- `kanjipipe/ingest/word_glosses.py`: `parse_word_glosses(path) -> list[tuple[int, str]]`
  — tolerant JSONL reader (skip blank/malformed lines; require integer `id` and
  non-empty stripped `ko`).
- `kanjipipe/loader.py`: `load_word_ko_glosses(conn, entries)` — for each
  `(word_id, ko)`, `INSERT INTO word_gloss (word_id, lang, text) VALUES (?, 'ko', ?)`.
- `kanjipipe/build_db.py`: `build(...)` gains optional keyword `word_ko_path=None`;
  when provided and the file exists, parse + load after `load_words` (and after
  `load_relations`, since relations need words but not word glosses). The main()
  default points at `sources/word_glosses_ko.jsonl`.
- Fixture `tests/fixtures/word_glosses_ko_sample.jsonl` + tests.

## 3. Components (app)

- `SharedModels.WordEntry` gains `meaningKo: String?`.
- `DictionaryClient.words` live SQL also fetches the word's `ko` gloss:
  per word, `SELECT text FROM word_gloss WHERE word_id = ? AND lang = 'ko' LIMIT 1`
  → `meaningKo`. `meaningEn` stays.
- `KanjiDetailView` words section: show the Korean meaning when the selected
  `appLanguage` is `.ko` and `meaningKo` is present; otherwise `meaningEn`.
  (A tiny pure helper `wordMeaning(_ word, _ language) -> String?` =
  `language == .ko ? (word.meaningKo ?? word.meaningEn) : word.meaningEn`.)

## 4. Testing

- `parse_word_glosses`: fixture with valid lines, a blank line, a malformed line,
  a line missing `ko` → only valid `(id, ko)` tuples; whitespace `ko` skipped.
- `load_word_ko_glosses`: seed a `word` row; load `(id, "산")` → a
  `word_gloss(word_id, 'ko', '산')` row exists.
- `build_db` integration: pass a small `word_glosses_ko.jsonl` fixture keyed to
  the fixture words' ids; assert a known word has a `ko` gloss.
- App: `wordMeaning` helper unit test (ko vs en selection + fallback);
  `DictionaryClient` integration — `words` returns `meaningKo` for a word that
  has one (after the real DB is rebuilt with ko; for the test, a word that has a
  ko gloss in the bundled DB — so this assertion lands AFTER the regen/re-bundle
  step; until then assert `meaningKo` is nil and `meaningEn` non-nil).
- Build/pipeline suites green.

## 5. Build order

1. Pipeline: `parse_word_glosses` ingester + `load_word_ko_glosses` +
   `build_db` `word_ko_path` stage + fixtures + tests (TDD). `.gitignore`
   negation for `word_glosses_ko.jsonl`.
2. App: `WordEntry.meaningKo` + `DictionaryClient.words` ko fetch + `wordMeaning`
   helper + `KanjiDetailView` display + tests (TDD where pure).
3. (Controller, separate) Generation run: export all `(id, surface, reading, en)`
   from `out/kanji.sqlite`, batch (~250/batch), parallel subagents produce
   `{id, ko}` → assemble `sources/word_glosses_ko.jsonl`; rebuild
   `out/kanji.sqlite` with `--word-ko`; re-bundle into the app; verify a sample
   word shows Korean.

## 6. Non-Goals / Follow-on

ja/zh word meanings; word frequency ranking; per-sense word glosses. Only ko is
added here (en already present).
