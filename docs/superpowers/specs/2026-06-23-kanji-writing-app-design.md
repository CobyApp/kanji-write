# Kanji Writing App — Design

Date: 2026-06-23
Status: Approved (brainstorming) — ready for implementation planning
Repo: https://github.com/CobyApp/kanji-write

## 1. Purpose

An iPad app for memorizing Japanese **jōyō kanji (常用漢字, 2,136 chars)** by
writing them with a pressure-sensitive Apple Pencil. The learner follows a
study plan ("finish in 10 days / 2 weeks / 1 month"), and each day writes a set
of kanji while seeing: meaning gloss, readings, usage words, example sentences,
and (briefly) synonyms / antonyms.

Fully **offline** native iPadOS app. Multilingual: Korean / Japanese / Chinese /
English — a single language selection drives both UI and learning content.

## 2. Scope & Non-Goals

In scope:
- All 2,136 jōyō kanji, classified by **both** axes: school grade (小1–中学)
  **and** JLPT level (N5–N1).
- Pressure-sensitive writing canvas with stroke-order guides.
- Study plans with daily distribution + progress tracking + light review.
- Four-language native content (meanings, readings, words, sentences,
  synonym/antonym).

Non-goals (v1):
- Strict handwriting / stroke-order recognition (only lightweight hinting).
- Cloud sync, accounts, social features, a backend server.
- Traditional-Chinese (zh-Hant) UI (zh-Hans only for v1; schema leaves room).

## 3. Architecture — two independent sub-projects

```
kanji-write/
├── data-pipeline/     # ① Data acquisition: open data + LLM gap-fill → kanji.sqlite
└── app/               # ② iPad app: reads the bundled kanji.sqlite (read-only)
```

The **data pipeline is built first** — it is the riskiest part and the
prerequisite for everything in the app. The app consumes its output
(`kanji.sqlite`) as a read-only bundled asset.

Two distinct stores at runtime:
- **Dictionary DB** — `kanji.sqlite`, generated by the pipeline, bundled into
  the app, read-only (GRDB.swift).
- **User store** — writable (SwiftData): study plans, per-kanji progress, saved
  ink (PKDrawing), settings. Never mixed with the dictionary DB.

## 4. Data model (dictionary DB, read-only)

Sketch (final DDL produced during pipeline implementation):

- **kanji** — `id`, `literal`, `codepoint`, `stroke_count`, `grade`
  (1–6, 8=中学), `jlpt_level` (N5–N1, nullable), `freq_rank` (nullable),
  `radical`, `kanjivg_id`.
- **reading** — `kanji_id`, `lang_axis` (`on`/`kun` for JA, `pinyin` for ZH,
  `eum` for KO), `value`, `is_common`. (Korean reading = 음; the 훈 lives in the
  KO gloss.)
- **gloss** — `kanji_id`, `lang` (`ko`/`ja`/`zh`/`en`), `text`. KO holds the
  traditional 훈+음 form ("메 산"); other langs hold a native meaning gloss.
- **stroke_order** — `kanji_id`, `svg` (KanjiVG paths), `stroke_count`,
  per-stroke order metadata (path + order index).
- **word** — `id`, `surface`, `reading_kana`, `freq`/`is_common`, JLPT tag.
- **word_kanji** — `word_id`, `kanji_id` (a word links to the kanji it contains).
- **word_gloss** — `word_id`, `lang`, `text`.
- **sentence** — `id`, `text_ja`, links to `word`/`kanji`.
- **sentence_translation** — `sentence_id`, `lang` (`ko`/`ja`/`zh`/`en`), `text`.
- **relation** — `word_id_a`, `word_id_b`, `type` (`synonym`/`antonym`).
- **similar_kanji** (optional) — `kanji_id`, `similar_kanji_id` — visually
  confusable kanji, surfaced as a small "비슷한 한자" hint.

All multilingual tables carry all four languages; the app shows only the
selected language.

## 5. Data pipeline (`data-pipeline/`, Python)

Per-source ingesters → merge → LLM gap-fill → validation → single SQLite.

**Sources & licenses**

| Source | Provides | License |
|---|---|---|
| KANJIDIC2 (EDRDG) | kanji core, on/kun, EN meanings, KO 음, pinyin, stroke count, radical, grade | CC BY-SA 4.0 |
| KanjiVG | stroke-order SVG paths, per-stroke order | CC BY-SA 3.0 |
| Unihan (Unicode) | variant mappings (新字体↔正字체), extra pinyin/Korean | Unicode license |
| JMdict (EDRDG) | usage words containing each kanji, glosses, `<ant>`/`<xref>` | CC BY-SA |
| Tatoeba | example sentences w/ ja+ko/ja/zh/en translations | CC BY 2.0 FR |
| Japanese WordNet (NICT) | synonym/antonym relations | free (NICT terms) |
| Korean 급수/교육용한자 dataset | 훈음 ("메 산") | per-dataset (verify) |

**Stages**

1. **KANJIDIC2** → kanji core + readings + EN meaning + KO 음 + pinyin.
2. Filter to jōyō (grade 1–8); merge a **JLPT N5–N1 list** (separate dataset —
   KANJIDIC2's `<jlpt>` is the pre-2010 4-level scale and must be overridden).
3. **KanjiVG** → stroke-order SVG/paths keyed by codepoint.
4. **JMdict** → words per kanji (ranked by commonness) + word glosses.
5. **Tatoeba** → sentences with ja + ko/ja/zh/en translations; link to
   words/kanji.
6. **WordNet-ja + JMdict ant/xref** → synonym/antonym relations.
7. **Korean 훈음** dataset → KO gloss 훈+음; map 新字体↔정자체 via Unihan
   variants (most jōyō match directly; only a few hundred differ).
8. **LLM gap-fill (Claude)** — for thin native fields (ZH 中文 meaning,
   KO 훈 where the dataset misses, JA monolingual gloss) and synonym/antonym
   curation: produce structured JSON, then a **review / spot-check pass**.
   Generated rows are flagged (`source = 'llm'`) so coverage and trust are
   auditable.
9. **Validation** — schema checks + a **coverage report** (fill rate per field
   per language) + dedupe. Hard gates (build fails if unmet): every kanji has
   ≥1 reading, an EN meaning, a gloss in all 4 languages, and stroke-order data.
10. **Emit** — versioned `kanji.sqlite` → app bundle.

Raw downloads live under `data-pipeline/sources/` (gitignored, fetched by a
script). Output `kanji.sqlite` is versioned and copied into the app bundle.

**Attribution**: the app ships an attributions screen citing all CC BY-SA / CC BY
sources and noting the share-alike obligation on the bundled data.

## 6. Writing engine (app)

- **PKCanvasView** for free pressure/tilt capture, custom brush (no default tool
  picker).
- **KanjiVG stroke-order guide** overlaid on the canvas, three modes:
  trace (full guide + numbered order) → free (faint outline, toggle) → test
  (no guide).
- v1 stroke-order feedback is lightweight (stroke-count / order hints), not full
  recognition. Saved attempts persist as PKDrawing in the user store.

## 7. Study plan

- Learner picks an **axis** (grade or JLPT) + **level/range** + **duration
  preset** (10일 / 2주 / 1달 / custom) → kanji distributed across days, ordered
  by grade/JLPT then frequency.
- Daily session: today's kanji → per kanji a study card (gloss, readings, words,
  sentences, synonym/antonym) + writing canvas → mark done.
- Light SRS review (toggle) resurfaces learned kanji; progress dashboard (streak,
  % complete).

## 8. Internationalization

Single language selection (ko / ja / zh-Hans / en) drives **both** UI strings
(iOS String Catalog) **and** learning content. Korean → Korean UI + 한글 훈음.
The dictionary DB holds all four languages; the app renders only the selected
one.

## 9. Testing

- **Pipeline**: per-source parser unit tests (fixtures), coverage assertions
  (the stage-9 hard gates), schema validation, dedupe tests.
- **App**: unit tests for plan-distribution logic, SRS scheduling, and the DB
  query layer; snapshot tests for the study card. PencilKit ink itself is
  manual QA; only the save/load plumbing for PKDrawing is automated.

## 10. Tech stack

App (targets the **latest stable iOS/iPadOS** — no backward-compat constraint;
free to use the newest APIs):

- **SwiftUI** — UI layer.
- **TCA (The Composable Architecture, pointfree)** — app architecture / state
  management. Features are modeled as composable `Reducer`s with explicit
  `State`/`Action`; side effects (DB reads, ink persistence, timers) run through
  TCA `Effect`s and injected dependencies (`@Dependency`), which keeps reducers
  pure and unit-testable with `TestStore`. The study-plan, study-card, writing,
  and progress flows each become a feature reducer.
- **Tuist** — project generation & modularization. The app is split into Swift
  packages/modules (e.g. `Features`, `DictionaryClient`, `UserStore`,
  `WritingCanvas`, `DesignSystem`) wired by a `Project.swift` manifest, so the
  Xcode project is generated and not hand-maintained.
- **PencilKit** — pressure/tilt writing canvas.
- **GRDB.swift** — read-only access to the bundled `kanji.sqlite` dictionary DB
  (wrapped behind a `DictionaryClient` TCA dependency).
- **SwiftData** — writable user store (plans, progress, saved `PKDrawing`),
  wrapped behind a `UserStore` TCA dependency.
- **iOS String Catalog** — i18n (ko/ja/zh-Hans/en).

Pipeline: Python (lxml for XML sources, sqlite3), Claude API for gap-fill.

## 11. Build order

1. **data-pipeline** (this is specced/implemented first) → produces a validated
   `kanji.sqlite` passing all stage-9 coverage gates.
2. **app** — bundle the DB, then build writing engine → study card → study plan →
   progress/SRS → i18n polish.

Each sub-project gets its own implementation plan (spec → plan → build).
